## 2026-07-01 — Fixed cache-key collision in gift-recommendation module (HIGH security)

## 2026-07-02 — Ingestion pipeline design: Awin product feeds (primary) + Amazon PA-API (secondary)
- Context: Product owner confirmed Awin publisher account and Amazon Associates/PA-API account are active. eBay is explicitly out of scope for now. Markets are Portugal and Spain (EUR). Backend is Spring Boot / PostgreSQL+pgvector (not Firestore — the product store is PostgreSQL; Firestore holds only social/user data). A full ingestion pipeline design was requested covering API choice, merchant prioritisation, normalisation, pre-filtering, deduplication, scheduling, and module placement.
- Decision: Awin ingestion uses the Product Data API v3 (JSON, paginated) rather than flat-file feeds at this scale — avoids SFTP infrastructure while the catalog is under 500k products. Feed runs are scoped to a curated allow-list of PT/ES merchant programmes per gift vertical. Amazon ingestion uses PA-API 5.0 SearchItems + GetItems operations against the amazon.es locale, with a keyword matrix per WiseGift category, respecting the 1 req/s starting rate limit via a token-bucket. Both sources share a single normalisation layer inside the existing `catalog` Spring module (no new module needed): `AffiliateClient` port is already in place; the implementation adds `AwinFeedIngestor` and `AmazonPaApiClient` adapters alongside the existing `AwinApiClient` (which should be promoted to feed-mode) and `AmazonCuratedClient` (which is a static YAML stub and should be replaced). The `ProductFeeder` keyword-loop is replaced by a feed-oriented orchestrator. Category taxonomy in `ProductCategoryKeywords` is misaligned with `data.md` canonical categories — these must be reconciled before the real ingestion runs (this is a pre-condition, not a blocker for the skeleton). Upsert strategy: `existsByProviderIdAndProviderProductId` check is retained for deduplication; price/image updates use JPA `save()` on the existing entity (UPDATE path). `active` gate is enforced after image URL validation. Scheduling: Awin full-feed daily at 02:00 UTC via `@Scheduled(cron)`; Amazon keyword sweep daily at 03:00 UTC. Both run inside the catalog Spring process — no separate CLI or new module. Roadmap: (1) fix taxonomy alignment, (2) wire Awin feed mode, (3) wire Amazon PA-API, (4) add pre-filter and image validation gates, (5) replace static YAML seeder with live data.

(c) Running ingestion in the catalog web process risks OOM under a large feed run; a dedicated `@Scheduled` thread pool is recommended (product owner decision needed). ## 2026-07-02 — Recommendation quality impact of user-contributed products assessed; hybrid strategy defined
- Context: Product owner evaluated a browser extension model where users clip products from any website into the shared catalog. The privacy-legal-advisor had already flagged the extension as not cleared to build in its proposed form (ToS, copyright, and browser-store policy risks). This assessment covers how user-contributed products would affect recommendation quality if the feature proceeds in a reduced-risk form.
- Decision: User-contributed products hurt recommendation quality in the short-to-medium term through four structural problems: (1) popularity bias — user clips reflect what users browse, not what recipients want, causing over-representation of Technology and Fashion and under-representation of Experiences; (2) metadata quality degradation — scraped product data is lower quality than affiliate-validated data, producing noisier embeddings; (3) no moderation floor — without a pipeline, low-quality clips enter the active catalog before any quality check; (4) category coverage gaps — the structural gap in Experiences is not fixed by user clips and may be masked by apparent catalog growth in other categories. One genuine positive case exists: users can clip unusual, artisanal, high-specificity gifts that affiliate algorithms cannot surface, particularly from merchants without Awin/Amazon programmes. This positive case is only realisable under three conditions: (a) the clip passes the same pre-filter quality gates as affiliate products; (b) it has at least one cross-user engagement signal (save by a user other than the clipper) before entering recommendations; (c) a recommendation slate diversity constraint caps user-contributed results at 2 of 5. If the feature proceeds, user-contributed products must use provider_id = "user_clip", land in active = false at ingest, and require a cross-user save gate before activation. The LLM prompt must cap user-clip results at 2 of 5. Per-category, per-source product counts must be monitored; if user clips exceed 40% of any category's active products, ingest for that category halts. The full hybrid strategy and engagement gate design are documented in docs/core/recommendations.md Section 5.
- Verdict to product owner: do not add user-contributed products to the active recommendation pool until the engagement gate, moderation pipeline, and per-source monitoring are in place. The positive case is real but narrow; the damage cases are structural and immediate.
- Made by: recommendations-specialist

## 2026-07-02 — Diagnosed "No products found in DB" in production gift-recommendation service
- Context: Production returned "No products found in DB for the given criteria" from `GiftRecommendationRagEngine` even though the DB held 176 active products with country='ES'. The log is emitted at `GiftRecommendationRagEngine.java` line 45 when `retrievedProducts.isEmpty()` is true.
- Decision: Root cause is that all 176 products have a NULL `embedding` column in the production PostgreSQL instance. The SQL query in `ProductRepository.getFindTopKByEmbeddingQuery` (lines 100-127) includes the predicate `1 - (embedding <=> :embedding::vector) > :match_threshold` (MATCH_THRESHOLD = 0.15). In PostgreSQL, `NULL <=> any_vector` returns NULL, so `1 - NULL` is NULL, and `NULL > 0.15` evaluates to false — every row fails the filter and zero rows are returned. The embedding column is populated by the catalog module's ingestion pipeline, which calls the OpenAI Embeddings API (text-embedding-3-small). The most probable cause is that `OPENAI_API_KEY` is missing or invalid in the Render production environment for the catalog service, causing the embedding step to fail silently during ingestion. Immediate fix (no code change): confirm `OPENAI_API_KEY` is set on the Render catalog service, then trigger a re-ingestion or back-fill to populate the embedding column. Three follow-up code hardening items: (1) add `AND embedding IS NOT NULL` to the WHERE clause in `getFindTopKByEmbeddingQuery` to make the filtering intent explicit; (2) add a null/empty-array guard in `GiftRecommendationRagEngine` after `embeddingService.embed()` to return an empty list with a WARN log rather than propagating a SQL error; (3) `toPgVectorLiteral` returns `"[]"` on null/empty input which causes a PostgreSQL cast error — also handled by guard (2). Diagnosis confirmed by: tracing the full call chain through `GiftRecommendationRagEngine` → `RecipientEmbeddingService` → `ProductRepository.findTopKByEmbedding` → `getFindTopKByEmbeddingQuery`; reading `application.yml` (`OPENAI_API_KEY` env var referenced for embedding model); reading `application-production.yml` (no override of the OpenAI key); reading `gift-recommendation/docker-compose.yml` (passes `OPENAI_API_KEY` from host env, confirming it must be set externally).

## 2026-09-29 — Resolved 6 open questions from the docs/core rewrite
- Context: The six open questions flagged in the docs/core rewrite entry above (three per doc) needed to be settled before the first implementing PR so the ingestion, event, and recommendation code has a stable spec to build against. Each is small on its own but they compound if left unresolved. During the discussion the PO also surfaced a real ambiguity in the "missed reconciliation" concept that the original draft glossed over.
- Decision:
  1. **Deactivation threshold on missed nightly reconciliation** (`data.md` §3). A product is marked `available=false` after **2 consecutive *successful* reconciliation runs** that did not observe it. A run counts as successful only if `catalog_sync_runs.status='ok'` AND `products_seen_count` is within ±10 % of the last known catalog size. Failed / partial runs are no-ops for the counter — a crashed nightly job or a Shopify 5xx must not self-inflict a fleet-wide deactivation. Introduces a small operational table `catalog_sync_runs` (`tenant_id`, `started_at`, `finished_at`, `status`, `products_seen_count`, `pages_fetched`) that also backs the webhook-health indicator in the admin sync-status panel. The row remains in the DB after deactivation; the existing §7 30-day soft-delete window governs hard removal. **Why the "successful run" qualifier**: the original draft's "2 consecutive misses" heuristic conflated three failure modes (product actually gone / our nightly job crashed / Shopify-side transient outage). PO surfaced this — the qualifier is what makes the heuristic operationally safe.
  2. **`intent_form_schema_version` on `intent_submitted` from day one** (`data.md` §5). Every `intent_submitted` event carries an explicit `intent_form_schema_version` column on the event row. Rationale: the v2 purchase-outcome learning loop will read months-old events across schema upgrades (verticalised intent packs are explicitly post-MVP), and there is no way to backfill a schema version onto events written before the column existed. Cost is one integer column per event; benefit is a lossless history.
  3. **Per-tenant `daily_spend_cap` column, nullable, default NULL = plan constant** (`data.md` §10). The kill-switch threshold ships as a nullable column on the tenant record. NULL falls through to the per-plan constant at check time; support sets it explicitly only for pilots that need custom headroom or outlier tenants that need a bespoke cap. No runtime lookup complexity. The per-plan constants themselves remain TBD at first pilot (not resolved here — flagged as still-open in `recommendations.md` §10).
  4. **Cache hit-rate: 60 % design target, operating band 40 %–85 %, not an SLA** (`recommendations.md` §4.5). Below 40 % → investigate cost blow-up (signature granularity / TTL / cache-key drift). Above 85 % → investigate staleness (signature likely too coarse). Reported hourly in cost telemetry, per tenant. Not customer-facing. Tunable during pilots — a target-not-SLA framing avoids locking us into a number before we've seen real traffic.
  5. **Pilot catalog floor: 200 SKUs** (`recommendations.md` §3.3). Below 200 the widget is re-shuffling near-everything and lift is unmeasurable — polite-decline for pilot. Pilots between 200 and 500 SKUs ship with an internal flag "limited lift-measurement power" so the case study does not over-promise significance. Well below the ICP floor of 1k SKUs to keep the pilot pool wide. The archived B2C `recommendations.md` used a 100-SKU guess; raised to 200 because significance-testing on holdout requires enough SKUs for the widget's slate composition to differ meaningfully across sessions.
  6. **Sonnet escalation: boolean per tenant at MVP** (`recommendations.md` §6.1). Per-flow override (gift-intent on Sonnet, self-intent on Haiku) is the more surgical design and maps cleanly to a Growth-tier pricing story — but it depends on pilot data showing Sonnet gives meaningfully better gift recs, and we don't have that. Ship boolean now; unbundle to per-flow once one pilot shows a clear Sonnet lift on gift intent. Direct consequence: `tenants.feature_flags` JSONB column must land in `architecture.md` §8 and in the first tenant-module PR — it is now required, not optional.

## 2026-09-29 — Widget consent for EU: no Consent Mode integration at MVP; ship escape hatch
- Context: Spec had an open question on whether WiseGift's widget needed a cookie-consent integration on day one. GDPR + ePrivacy Directive Art. 5(3) requires prior consent for storing information on a user's terminal equipment unless it is "strictly necessary for the provision of an information-society service explicitly requested by the user." Our widget stores a first-party UUID in localStorage for attribution + holdout assignment — the exact grey zone.
- Decision:
  1. **Ship without Consent Mode integration at MVP.** Our data flow — first-party UUID, no PII, no cross-site tracking, 30-day sliding TTL, EU-only hosting, never linked to the merchant's customer DB — sits inside the CNIL-line "strictly-necessary measurement" reading of ePrivacy Art. 5(3). GDPR Art. 6(1)(f) legitimate interests is the belt-and-braces basis. Position paper at `docs/legal/consent-position.md` is the artefact we hand to pilot DPOs when asked.
  2. **Ship the escape-hatch code path from day one.** The widget reads `window.Shopify.customerPrivacy.currentVisitorConsent()` at bootstrap. Three states: (a) consent granted or unknown-in-permissive-jurisdiction → mint UUID, write localStorage, deterministic holdout, emit events; (b) consent denied → no localStorage write, no `wg_session` identifier, no event emission; recs still fetch server-side, holdout falls back to a per-request coin flip, backend records `attribution_mode=degraded` for honest reporting; (c) consent changes mid-session → widget re-reads on `visitorConsentCollected`, mints from that point forward, no retroactive backfill.
  3. **Per-tenant `consent_mode_required BOOLEAN` on the tenant record** (default `false`). Lets support flip a stricter merchant into fallback-always without a code change. New column landing in a follow-up architecture.md §8 pass.
- Rejected alternatives:
  - **Ship Consent Mode integration as default.** Blocks 90 % of the pilot pool (CNIL-line jurisdictions) from getting attribution data with no incremental privacy benefit. Also adds bootstrap latency against the 100 ms TTI budget.
  - **Document the escape hatch but don't ship the code.** The residual risk is exactly the case where we need to ship in a hurry — if the first German pilot's DPO asks on day 3, we cannot bolt this on. Ship it now.
  - **Set the session ID server-side.** Doesn't help — an identifier is an identifier under ePrivacy regardless of where it originates; the trigger is storage on the user's device.

First DE pilot's DPO likely to require Consent Mode from day one. Italy's Garante is the second-most-likely to push back. Both mitigated by the shipped escape hatch (flip `consent_mode_required=true` on the tenant, done).

## 2026-09-29 — Widget theming: two-layer model (Shopify auto-inherit + merchant design tokens)
- Context: The Frozen MVP scope entry pinned Shadow DOM isolation for widget CSS (safety — widget can never break the merchant's theme) but that also means the widget cannot inherit merchant styling by default. The existing `widget_config` table exposed only `brand_accent_color` and `border_radius_px` — roughly zero personalisation. PO surfaced the concern: for Shopify, the widget "should keep more or less the look and feel of the merchant". Without a theming answer, every widget looks like a generic WiseGift widget dropped into the storefront — a trust and conversion problem.
- Decision: two-layer theming model, targeted at Shopify for MVP with a platform-agnostic fallback for VTEX / SFCC.
  1. **Layer 1 — Shopify auto-inheritance (zero merchant config).** CSS custom properties cross Shadow DOM boundaries by design. The widget's internal CSS references standard Shopify Theme Editor variables via `var()` with WiseGift defaults as the fallback: `color: var(--wg-accent-color, var(--color-accent, #6c47ff))`. Modern Shopify themes (Dawn and derivatives) expose `--color-accent`, `--color-foreground`, `--color-background`, `--font-body-family`, `--font-heading-family` — the widget picks them up automatically without any admin configuration. Merchants on themes that don't expose them fall through to layer 2 or the WiseGift default.
  2. **Layer 2 — Merchant design-token overrides.** A small set of tokens the merchant can set explicitly in the admin dashboard. Stored in `widget_config.theme_tokens` JSONB, nullable, defaults `{}` — only explicit overrides live there. At widget mount, non-null tokens are applied as `--wg-*` CSS custom properties on the host element via inline `<style>`, taking precedence in the `var()` fallback chain. Token list (8 total): `accent_color`, `text_color`, `background_color`, `font_family`, `heading_font_family`, `border_radius_px` (reuses existing column, not duplicated in JSONB), `spacing_scale` (preset enum `compact | cozy | roomy`), `card_shadow` (preset enum `none | subtle | medium`).
  - `border_radius_px` stays on `widget_config` as its own column (existing) rather than migrating into `theme_tokens`. `brand_accent_color` (existing column) is superseded by `theme_tokens.accent_color` but kept for backward-shape reasons; consolidation deferred to the tenant-module PR.
  - Precedence at widget runtime: inline `--wg-*` from admin overrides → Shopify theme variable → WiseGift default. All expressed inside a single `var()` chain per property, so the browser resolves the cascade natively — no widget code branches on tenant type.
- Rejected alternatives:
  - **Full Shadow DOM isolation only (status quo).** Safest, but widget looks foreign to the merchant's storefront. Rejected — the trust cost outweighs the safety win now that we've designed a mechanism that keeps isolation intact.
  - **`::part` slots for merchant-CSS overrides.** Powerful (merchant can style any widget internal), but requires the merchant to write CSS. Not viable for "install and forget" merchants. Deferred to v2 if power users ask.
  - **Custom CSS injection by the merchant (raw stylesheet).** Same problem as `::part` plus a real risk of merchants sending broken CSS that we can't validate. Rejected.
  - **Larger token set (typography scale, colour palette per state, focus ring, etc.).** Cost is admin-UX complexity and merchant decision fatigue. Eight tokens covers 90 % of visual coherence; expand later based on pilot feedback.
- Consequences:
  - `docs/product/spec.md` — new feature block `Merchant admin — Widget theming` added between `Widget configuration` and `Placements`; cross-reference added to `Widget configuration` to avoid overlap. 13 acceptance criteria including live preview, per-token reset, auto-inherit indicator (Shopify only), WCAG AA contrast warning, font-loaded-on-storefront warning.
  - `docs/engineering/architecture.md` §8 — `widget_config.theme_tokens JSONB` column added; `brand_accent_color` and `border_radius_px` column notes updated to describe their new roles in the fallback chain.
  - `docs/engineering/architecture.md` §10.5 — new subsection "Theming and CSS variable inheritance" covers the two-layer model, the `var()` fallback chain with code example, bootstrap wiring (non-null tokens applied inline on host element), `SPACING_SCALES` and `CARD_SHADOWS` preset tables. Bundle-size sub-budget: theming logic must add < 1 KB gzipped to `widget.js`; frontend-engineer's initial estimate is 400–600 bytes.

  - **Auto-inherit banner wording** — the "N of 8 style values inherited from your theme" indicator requires probing which Shopify CSS variables the theme actually exposes. Detection mechanism (static list vs live probe of the merchant's storefront from the admin) TBD at first widget PR.

## 2026-09-29 — Full platform-agnostic column sweep across the schema
- Context: The `tenants ↔ platform_credentials` split entry above removed Shopify-specific columns from `tenants` but left the same leak pattern intact everywhere else — `shopify_product_id` on `tenant_products`, `shopify_variant_id` on `tenant_product_variants`, `source_shopify_product_id` / `recommended_shopify_product_id` on `precomputed_recs`, `shopify_product_id` on `events`, `shopify_order_id` on `orders_attributed`, plus `handle` (a Shopify vocabulary noun) on `tenant_products`. PO surfaced the inconsistency: "all the columns of the tables can't have platform-specific columns." The prior sweep was scope-limited; this one completes it.
- Decision:
  1. **All `shopify_*_id` column names renamed to `platform_*_id`** across every table:
     - `tenant_products.shopify_product_id` → `platform_product_id`
     - `tenant_product_variants.shopify_variant_id` → `platform_variant_id`
     - `precomputed_recs.source_shopify_product_id` → `source_platform_product_id`
     - `precomputed_recs.recommended_shopify_product_id` → `recommended_platform_product_id`
     - `events.shopify_product_id` → `platform_product_id`
     - `orders_attributed.shopify_order_id` → `platform_order_id`
     - `orders_attributed.line_items` JSONB field key `shopify_product_id` → `platform_product_id`
  2. **All renamed `*_id` columns retyped from `BIGINT` to `VARCHAR(64)`.** Consistent with `platform_shop_id VARCHAR(64)` from the prior split. Shopify's numeric IDs stringify losslessly; VTEX and SFCC use non-numeric IDs. Marginal index cost at MVP scale; the type change is what actually makes the columns cross-platform, not just the rename.
  3. **`tenant_products.handle` renamed to `slug`.** `handle` is Shopify vocabulary; `slug` is the generic web term (VTEX uses `slug`, SFCC uses "URL keyword"). Column note now explicitly documents the mapping to each platform's native name so it's discoverable.
  4. **Notes kept universal.** `product_type` and `tags` column notes were rewritten to describe the concept ("category/type", "labels") rather than reference "Shopify product type field" and "Shopify tags" — the column names were already generic but the notes were leaking.
- Not renamed:
  - `platform_credentials.platform` column values (`shopify`, `vtex`, `sfcc`) — those ARE the platform identifiers by definition.
  - The `handle` reference inside the `slug` column note — that is documentation of the Shopify-native equivalent, not a schema leak.
  - `data.md` prose references to the Shopify webhook payload's `shop_domain` field — that's the payload field name, an inherently Shopify concept, not a schema column.
- Rejected alternatives:
  - Prefix `external_*` instead of `platform_*` — would work but inconsistent with the already-committed `platform_shop_id` / `platform_shop_domain` naming.
  - Keep `BIGINT` for `_id` columns and just rename — defeats the purpose; non-numeric platform IDs would need another migration.
  - Drop the ID prefix entirely and rely on tenant scoping — reads ambiguously against the row's own `id` PK column.
- Consequences:
  - Every doc that referenced these column names got a pass: 5 references in `spec.md`, 4 in `data.md`, 3 in `recommendations.md`, plus 8 in `architecture.md` itself (schema tables + §5 precomputed_recs prose + §9.4 event API body shape).
  - The API contracts in `architecture.md` §9 and `spec.md` recommendation/event API sections now expose `platform_product_id` in request/response bodies. Widget code (not yet written) will read this field name from day one; there is no pre-existing widget to migrate.
